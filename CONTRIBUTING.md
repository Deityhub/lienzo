# Contributing to Lienzo

Thanks for helping. Bug reports, ideas, documentation fixes and code are all welcome. By taking part you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md). For a security problem, please follow [SECURITY.md](SECURITY.md) instead of opening an issue.

## Ways to help

- **Report a bug or suggest something:** open a [GitHub issue](https://github.com/Deityhub/lienzo/issues). For a bug, say what you did, what you expected, what happened, and your browser. A screenshot or a `.lienzo.json` file that shows it helps.
- **Ask a question or share an idea:** use [GitHub Discussions](https://github.com/Deityhub/lienzo/discussions).
- **Send a change:** see below. For anything bigger than a small fix, please open an issue first so we can agree on the approach before you spend time on it.

## Set up

You need Node.js 22 (see `.nvmrc`) and Yarn 4 (`corepack enable` picks the pinned version).

```bash
git clone https://github.com/<your-username>/lienzo.git
cd lienzo
yarn install
yarn dev            # http://localhost:5173
```

## Make a change

1. Fork the repository and create a branch from `develop`, for example `feat/text-alignment` or `fix/resize-offset`.
2. Make the change, and add or update tests for it.
3. Run the same checks CI runs:

   ```bash
   yarn lint           # Prettier and ESLint
   yarn check          # types
   yarn test:unit:run  # unit and browser-component tests
   yarn test:e2e       # builds the app and runs the Playwright tests (Chromium)
   ```

   `yarn format` fixes formatting. The first time, run `yarn playwright install chromium`.

4. Open a pull request into `develop` and fill in the template.

### Pull request titles and commits

Pull requests are squash-merged, and the PR title becomes the commit message, so it must follow [Conventional Commits](https://www.conventionalcommits.org/) (CI checks this): `feat: add text alignment`, `fix: resize handle offset`, `docs: explain backups`. `feat`, `fix`, `perf`, `refactor` and `docs` appear in the changelog; `chore`, `ci`, `test` and similar do not.

### Code style

- TypeScript and Svelte 5 with runes (`$state`, `$derived`, `$effect`). State shared between components lives in `.svelte.ts` files.
- Keep pure logic (geometry, sorting, file formats) in `src/lib/utils` as plain functions with unit tests, apart from the components.
- Colours, spacing and radii come from the theme tokens in `src/app.css`, so both the light and the dark theme work. Please check a change in both.
- Interfaces must work with the keyboard and a screen reader: real buttons, labels for icon-only controls, visible focus, and touch targets of at least 44px on phones.

### Tests

- **Unit tests** (`*.spec.ts`) run in Node. Tests that need a browser (`*.browser.spec.ts`) run in Chromium.
- **End-to-end tests** (`e2e/`) run against a production build on port 4173. To keep them reliable on any machine:
  - wait for hydration (`waitForLoadState('networkidle')`) before the first click;
  - assert on the saved data (read from IndexedDB, in page units) rather than on screen pixels;
  - use `dragTo` for drags, and `hasTouch: true` for tap tests.

## Documentation and generated files

- Update the README and other docs when behaviour changes.
- If you add or remove a runtime dependency or a font, run `yarn notices` to refresh [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md).
- If you add a font, also regenerate the PDF export fonts with `python3 scripts/generate-pdf-fonts.py` (needs `fonttools` and `brotli`).
- The icons and the social image are generated by `yarn brand:assets`; the screenshots in the README by `yarn docs:screenshots`.

## Releases

Lienzo follows [Semantic Versioning](https://semver.org/) and keeps a [CHANGELOG](CHANGELOG.md) generated from the commit titles.

1. In GitHub, go to Actions, then **Prepare Release**, and run it on `develop` with `patch`, `minor` or `major`. It opens a `chore(release): vX.Y.Z` pull request that bumps `package.json` and the changelog.
2. Merge that pull request into `develop`.
3. Open a pull request from `develop` into `main` and merge it with a merge commit. The **Release** workflow tags the version and creates the GitHub release; the Docker image is published to GHCR and Docker Hub.

To run CI on the release pull request, add a personal access token as the repository secret `RELEASE_TOKEN`.
